# Orchestrator Prompt — Velm Agent Canvas

Copy everything below into Claude (or Claude Code) to kick off planning and implementation.

---

You are the lead orchestrator agent for a major new feature in **Velm**, my existing native Rust desktop app — a Miro alternative built with wgpu (GPU-accelerated canvas rendering), egui (chrome/UI), cosmic-text (text rendering), SQLite (per-board storage) plus a BLAKE3-addressed blob store, and a Loro CRDT document model (used for undo/history, not for real-time collaboration — Velm is explicitly single-player). It currently runs on macOS, with Apple Silicon officially supported, Intel buildable from source but untested, Windows planned but not yet built, and Linux not planned. The repo is at `github.com/ibrahimbisen/Velm`, built as eighteen crates.

Existing Velm capabilities you should know about before planning anything: an infinite pan/zoom canvas; boards that can be organized into folders, starred, and searched; a pen tool with smoothing and an eraser; 41 shapes including standard flowchart symbols; connectors that stay attached to shapes and re-route when either end moves; sticky notes and text boxes edited directly on the canvas with a real text caret; tables; kanban boards; auto-laying-out mind maps; bar/line/pie charts; link cards (paste a URL, get a card with title/icon/preview image); image embedding with deduplicated storage shared across boards; importing full Miro boards (including pen strokes, which no Miro API exposes) via clipboard paste or `.rtb` file; and export to PNG, PDF, SVG, and CSV. Velm deliberately does NOT do real-time multiplayer collaboration, playable video embeds, dark mode, or PDF rendering (PDF bytes are stored but not drawn yet).

Your job: plan, research, and coordinate implementation of a new capability called the **Agent Canvas layer** — turning Velm's existing frames, notes, and connector lines into a live multi-agent AI workspace, where AI coding/research agents run visibly on the board, can be wired together to communicate, and can be organized, scheduled, and orchestrated spatially. This is an *addition* to the existing app, not a fork or a rebuild, and not a separate app bolted on the side. Reuse Velm's current canvas engine, node system, connector system, note system, and CRDT document model wherever technically reasonable. Preserve Velm's core philosophy at every step: native performance, minimal memory footprint, no Electron-style bloat, no unnecessary idle resource use, no forced cloud dependency.

You are authorized to spawn sub-agents to research prior art, plan architecture, and implement individual pieces of this feature set. Coordinate their work yourself, resolve conflicts between their recommendations, and report back to me with a unified plan before writing large amounts of code. Ask me clarifying questions if something is genuinely ambiguous and blocks progress, but otherwise use your best engineering judgment and keep moving — don't stall on decisions you're equipped to make yourself.

## Background / inspiration — study these three tools in depth

Three existing tools directly inspired this feature. Research each one's actual implementation approach (docs, changelogs, any available source code, technical blog posts), not just its marketing description, before proposing Velm's architecture.

**Maestri** (`themaestri.app`; open-source clone at `github.com/zlh-428/open-maestri`) is a native macOS app, built entirely in Swift/SwiftUI with a custom Metal-based canvas engine — no web views, no Electron. Its core mechanic: place a terminal node on an infinite canvas, and that terminal runs a real CLI coding agent (Claude Code, Codex, OpenCode, Gemini CLI, etc.) via a PTY (pseudo-terminal). Each terminal node can have its own working directory. Drawing a connector line between two terminal nodes lets the agents inside them talk directly — one agent can literally type commands or prompts into another agent's terminal, enabling delegation and handoff without the human relaying messages. Beyond terminals, Maestri supports: Note nodes (markdown, with a raw/formatted dual view, image support, and note-to-note "chains" that agents can traverse to follow linked context); File Tree nodes; a "Portal" node (an embedded WKWebView browser, so you can preview/test a live site without leaving the canvas); freehand sketching for architecture diagrams; and shapes. Notes are saved as real `.md` files on disk, not locked inside an app database, so any agent (or the user, in any text editor) can read and write them directly — this is one of the most-praised features in user reviews. Maestri also ships "Ombro," an on-device AI companion (via Apple Intelligence, so it runs locally with no cloud calls) that watches canvas activity and generates a summary of what happened while the user was away. Performance-wise, Maestri uses viewport culling — off-screen terminal nodes keep their PTY processes alive and running, but stop being visually rendered, which is how it stays lightweight even with dozens of active agents. The open-source clone (`open-maestri`) additionally documents a local-only IPC layer: an `InterAgentServer` bound to `127.0.0.1` only (no external network exposure) that agent-to-agent messages route through via a small injected CLI tool, worth studying as a concrete, buildable pattern for the connector-based messaging feature below.

**MindPal Canvas** (`mindpal.space/canvas`) is a much lighter, cloud-based tool: an infinite canvas of chat-style agent nodes that can sit side-by-side or be chained in sequence, so the output of one agent's conversation feeds into the next as input. It has no live terminals and no agent-to-agent live communication in the Maestri sense — it's closer to a visual layout of branching chat trees. Its standout strength is broad file/context ingestion: users can feed in documents, audio, video, YouTube links, and websites, and chat with all of them as context. It also supports training an agent on a specific custom knowledge base so it stays scoped to that domain, and it can embed a finished agent onto external websites or apps as a deployable widget.

**OpenHands Agent Canvas** (`openhands.dev/product/canvas`; `github.com/OpenHands/agent-canvas`) is a browser-based, self-hostable UI and backend for running coding agents, built by the team behind OpenHands (formerly OpenDevin). Its standout architectural feature: every agent runs isolated in its own **git worktree**, so multiple agents can operate on the same repository in parallel without stepping on each other's file changes or needing separate full clones — all visible from a single dashboard. It's explicitly agent-agnostic: it connects to Claude Code, Codex, or any harness that implements the open **Agent Client Protocol (ACP)**, a JSON-RPC-based protocol where the client (Agent Canvas) initializes a session, sends prompts, and the agent streams updates back, requests permissions when needed, performs file/tool operations through supported client capabilities, and returns a turn result — this is the cleanest existing spec for "swap the underlying model/agent without changing the UI," and should heavily inform Velm's own provider-abstraction layer. OpenHands also supports role-based agents (e.g., "Frontend Developer," "Code Reviewer") that hand off tasks to each other; scheduled/automated runs (cron-style, polling, or event-driven, e.g. triggered by a GitHub issue or Slack message); a library of MCP tool connections and "Agent Skills" (markdown-defined behavioral extensions, compatible with formats like `.cursorrules` and `agents.md`); sub-agent delegation, where a parent agent can spawn and monitor sub-agents as independent conversations that inherit the parent's model config and workspace context; and — importantly — the ability to authenticate using an existing subscription (Claude Max, Codex Pro, Gemini Advanced) rather than metered per-token API billing, because ACP delegates execution to a locally-running agent process that already holds those credentials.

## Full feature list to design and build

Treat every feature below as user-approved and final. Do not silently drop, merge, or simplify any of them — if two features create a real technical conflict, stop and flag it with options rather than resolving it unilaterally.

### 1. Live agent nodes
Every frame on the canvas can become a live agent node: a node type that runs a real AI coding/research agent and streams its output in real time, the way a terminal or chat window would, but rendered natively inside Velm's own canvas (not an embedded web view). Decide during research whether this is best implemented via direct PTY hosting (Maestri's approach — good for CLI-based agents like Claude Code, Codex, Gemini CLI) or via the Agent Client Protocol (OpenHands' approach — good for provider-agnostic swapping) or a hybrid supporting both. Each agent node needs: a clear running/idle/error state indicator, its own working directory (for coding agents), and the ability to be freely resized, repositioned, and organized spatially alongside every other node type Velm already supports.

### 2. Two display modes per agent
Every agent node needs a way to control how much of its internal process is visible:
- **Raw mode**: shows every tool call, shell command, file read/write, and intermediate reasoning step the agent takes — equivalent to what the Claude Code VS Code extension currently shows, which is useful for debugging and trust but noisy for daily use.
- **Clean mode**: shows only the polished, conversational final output — equivalent to the experience of claude.ai, where you see the answer, not the scaffolding.
This must be toggleable per individual agent node (so you can run one agent in raw mode while everything else stays clean), and there should also be a global default setting so new agents inherit your preferred mode automatically.

### 3. Agent-to-agent direct communication
Reuse Velm's existing connector-line system (the same lines used to link shapes) as the mechanism for wiring agents together. When a connector links two agent nodes, the agents on either end can message each other directly and autonomously — delegating a sub-task, asking a clarifying question, or handing off completed work — without the user manually copying anything between them. This should visually distinguish an "agent connector" from a normal shape connector (e.g., a different line style or an animated pulse while a message is actively passing) so the user can tell at a glance which agents are wired together and when they're actively talking.

### 4. Git worktree isolation (opt-in)
For coding-focused agents, provide an optional per-project setting that, when enabled, automatically gives each agent its own isolated git worktree of the codebase, so multiple agents can work on the same repo simultaneously without their file changes colliding or requiring the user to manage branches manually. This must be off by default, since it adds disk usage and setup complexity, and should be a single clear toggle in the project's settings rather than something enabled per-agent inconsistently.

### 5. Custom role labels
Each agent node can be assigned a role, expressed as free-form text the user writes themselves (not a fixed dropdown of preset roles), such as "Frontend Developer," "Code Reviewer," "Research Assistant," or anything else. This role text should genuinely shape how the agent behaves and responds (i.e., it gets folded into the agent's system context, not just displayed as a label). Roles must be fully editable at any time, directly on the node.

### 6. Meta / general agent
A special agent type — a general-purpose assistant the user can talk to directly — that has the ability to reach into and edit other agents' configuration on the user's behalf: changing another agent's role, editing its notes, adjusting its rules, or reassigning its scope, all through conversation with the meta agent rather than the user manually clicking into each node one at a time. Think of it as an admin/control-plane agent for the whole board.

### 7. File tree nodes (per-agent scope)
A node type that displays a project's folder and file structure as a browsable tree, similar to a code editor's sidebar, so the user can see project structure directly on the canvas without opening a separate window. This must be scoped **per agent** — each agent gets its own file tree view, which can be limited to just the part of the project that agent is actually working on, rather than every agent always showing an identical full-project tree.

### 8. Note nodes (dual scope, real files on disk)
Markdown sticky notes on the canvas that agents can read as context or write into directly, functioning as shared or private memory. This feature has two hard requirements:
- **Dual scoping**: notes must support both a private per-agent scope (visible/writable only to one specific agent) and a shared per-project scope (readable/writable by every agent on that board) — the user must be able to choose which scope a given note uses, and both scopes need to coexist and be usable simultaneously.
- **Real files on disk**: notes must be persisted as actual `.md` files in the project's file system location, not hidden inside an internal app database — so the user (or any external tool) can open, edit, and version-control them directly, and agents read/write them as real files. Support note-to-note linking/chaining (as Maestri does) so an agent can follow a trail of connected notes for deeper context.

### 9. Orchestrator / meta agents with scoped territory and spawn limits
A distinct orchestrator agent type designed to manage other agents rather than do direct work itself. When placed on the canvas, an orchestrator can be assigned a specific spatial region of the board ("you are only responsible for this section") by the user selecting an area, and a hard cap on how many sub-agents it's permitted to spawn at once (e.g., "spawn up to 5 agents as needed"). This prevents an orchestrator from spawning an unbounded number of agents and overwhelming the board or the user's compute/API budget. The orchestrator should be able to spawn agents within its assigned territory autonomously, up to its cap, when it determines a task needs to be broken up.

### 10. Scheduled / triggered agents
Agents must be configurable to run automatically on a schedule (e.g., every day at 6 PM) rather than only when manually invoked. On completion of a scheduled run, the agent should be able to take one of several actions based on its results: report back to the user (e.g., a summary card or notification), hand off automatically to another connected agent, or take no action if nothing is warranted. Build the full scheduling configuration UI (schedule editor, trigger conditions, action selection) and the underlying logic now, in the initial implementation. The part that requires the app to be running continuously on a server rather than the user's local machine — so schedules fire even when the laptop is closed — can be explicitly deferred to a later phase; note this dependency clearly in your plan rather than blocking Phase 1 on it.

### 11. Hierarchical, granular rule system
Design a layered configuration system, conceptually similar to CLAUDE.md / `.claude` config files, but structured so rules cascade through multiple levels rather than existing as one flat file per project:
- **Global rules**: apply across the entire app, to every board and every agent, unless overridden.
- **Per-project rules**: apply to every agent on one specific board, and can override global rules.
- **Per-agent overrides**: apply to a single agent only, and can override both project and global rules — for example, setting a specific communication or output style ("talk to me formally") for just two particular orchestrators while every other agent uses the project default.
Each layer should clearly inherit from the layer above unless explicitly overridden, and the user should be able to see, at any level, which rules are inherited versus explicitly set at that level.

### 12. Voice control
Provide the ability to talk to an agent node out loud, as an alternative to typing, with the agent responding to spoken input the same way it would to typed input. This should be available per-agent (activate voice input on the specific node you're addressing) rather than only as a single global voice channel.

### 13. Embedded browser nodes (opt-in, RAM-gated)
A node type — similar to Maestri's "Portal" — that renders a live, interactive web page directly on the canvas, so the user can preview or test a website or app being built without leaving Velm. Because embedded browser engines are RAM-heavy and directly conflict with Velm's low-footprint design goal, this must be gated behind an explicit opt-in setting (disabled by default), and ideally only instantiates the actual browser engine when a browser node is created or made visible, not preloaded on app launch.

### 14. Visual agent output / selectable options
Agents must be able to embed images directly into their output on the canvas — screenshots, rendered previews, generated mockups, or diagrams — not just text. Specifically support the pattern of an agent presenting several visual options at once (e.g., "here are three UI directions I built") and letting the user click to select one, rather than only describing the options in words. This directly addresses a real limitation the user has hit with the Claude Code VS Code extension, which currently cannot display images or screenshots inline at all.

### 15. Away-mode summaries
When one or more agents work autonomously while the user is not actively watching the canvas, the app should compile a summary of what happened during that time — what each agent did, what changed, what needs the user's attention — and present it clearly when the user returns, rather than requiring them to scroll back through raw logs.

### 16. Multi-provider / bring-your-own-model support
Support signing in with multiple AI providers, including at minimum Claude, OpenAI, and Kimi, with the architecture designed to make adding further providers straightforward. Also support connecting a locally-run model — for example, a model the user is running on their own GPU — as a provider option alongside the hosted ones. Critically, provider/model selection must be assignable **per individual agent node**, not fixed once for the entire board, so a single canvas can have one agent running on Claude, another on a local model, and another on a different provider simultaneously.

### 17. Bring-your-own-subscription
Where technically possible, allow agent execution to run against the user's existing subscription (e.g., a Claude Max plan, a Codex Pro plan) rather than requiring separate, metered per-token API billing. Research how OpenHands achieves this through the Agent Client Protocol — by delegating execution to a locally-running agent process that already holds the user's existing credentials — and evaluate whether the same approach is viable for Velm's architecture.

### 18. Feed-in any file type as context
Agents should be able to ingest a broad range of file types as working context, not just plain text: documents (PDF, Word, etc.), audio, video, YouTube links, and general websites. This should integrate with Velm's existing file/image handling systems where possible rather than building an entirely separate ingestion pipeline.

### 19. Built-in web research capability
Build an MCP server (or an equivalent internal tool) into Velm that lets an agent perform web research in a way that behaves like a real human browsing session, rather than a raw API call — specifically to avoid the anti-bot blocking that plain automated fetches often trigger, which limits how well agents can currently do open-ended research. Research and propose a legitimate, robust implementation approach for this (e.g., a real but automated browser session with human-like behavior) — the goal is reliable, unblocked access to information for agents doing research tasks, not building something intended to evade security measures in a way that could be misused elsewhere.

## Constraints and priorities

- This is strictly an addition to the existing Velm codebase — its eighteen crates, its wgpu/egui/cosmic-text rendering stack, its SQLite + BLAKE3 blob storage, and its Loro CRDT document model. Reuse existing systems (frames, connectors, notes, canvas rendering/viewport culling, node persistence, undo/history) wherever they can reasonably serve the new agent features, instead of building parallel, duplicate systems.
- Preserve Velm's stated identity at every decision point: native, fast, minimal memory footprint, no Electron, no unnecessary idle resource use, no forced cloud dependency, no telemetry unless the user explicitly opts in. Any feature above that risks working against this (embedded browsers, always-on scheduling infrastructure, background agents running unattended) must be explicitly opt-in, never default-on, and should degrade gracefully (e.g., viewport culling for off-screen agent nodes, the way Maestri suspends rendering but keeps processes alive).
- macOS on Apple Silicon remains the primary target; don't introduce dependencies or design choices that would block Velm's existing or planned platform support (Intel macOS, eventual Windows).
- The nineteen features above are the complete, user-approved scope for this effort. If you believe a feature is technically unworkable as described, say so explicitly and propose an alternative — do not quietly narrow scope.
